## CRITICAL — ships today, App Store compliance risk

### Account deletion 500s for any user with settlement history
`src/PokerApp.Application/Features/Auth/Commands/DeleteAccount/DeleteAccountCommandHandler.cs:47`

The handler removes memberships, received invitations and refresh tokens, and anonymises
`SessionPlayer.UserId` — but never touches **Settlements** (`PayerUserId`/`ReceiverUserId`, required
FKs with `DeleteBehavior.Restrict`), **`SessionPlayer.LinkedUserId`** (Restrict), or **group
invitations the user SENT** (`InvitedByUserId`, Restrict). `context.Users.Remove(user)` then throws
`DbUpdateException` at `SaveChangesAsync`, which `ExceptionHandlingMiddleware` does not map — so the
live app returns a bare 500.

> **CORRECTED 2026-08-04** (the fix branch retracted two details of this finding, and PR #74
> supersedes its scope): the 500's body is `"An unexpected error occurred. TraceId: …"`, and
> ProfileScreen renders that body — the user saw a trace-id string, never the client fallback
> "Failed to delete account." (every server response carries a message, so the `??` fallback
> renders only on network-level failures where no response arrives at all). And the three Restrict blockers listed above were only the seeded reproduction;
> the full model has **eight** Restrict edges to Users, now pinned with the complete
> per-behavior FK inventory in `DeleteAccountFkIntegrityTests`.

Any user whose finished session ever had settlements calculated — **exactly the engaged users** —
cannot delete their account. iOS 1.1.1 is live; **App Store Guideline 5.1.1(v) requires working
in-app account deletion**, and the Danger Zone copy promises "permanently delete your account and
all your data." There is no backend test for `DeleteAccount`.

This is a CLASS: no handler that deletes a user-owned aggregate has an integration test proving the
delete actually succeeds against the real FK graph. The guard is an integration test per
delete-path, seeded with the FK shapes that exist in production.

**Disposition: its own slice, before any Q2 pillar work.** It is a live-compliance defect on a
shipped app; Q2 is polish by comparison.

**✅ RESOLVED PR #74** (merged 2026-08-04, after 4 disposition commits + 2 fleet rounds): FK fix
+ settlement-preservation guard (scoped to sessions with recorded settlements per owner decision)
+ `AccountDeletedAt` marker for the linked-guest shape + legacy-money-row re-keying + full FK
inventory ratchet (19 edges, all delete behaviors, not just Restrict). See PR #74's commit history
for the complete arc; the "Deferred findings" section below records what was deliberately NOT
fixed in that slice.

## MAJOR — grouped by theme

### Money/data correctness on the front door
- **Home has no error state.** `HomeScreen.tsx:160` — three of the seven load calls have no
  `.catch`; any failure rejects the batch into a silent `catch {}`, and the hero then renders
  `stats?.totalProfitLoss ?? 0` as an animated **₪0 "Break even"** with "0 sessions". A network
  blip shows a returning user confidently wrong money. *Never `?? 0` for money* is the class rule.
  **✅ RESOLVED PR #75** (merged 2026-08-05): independent `.catch` on all seven calls; `statsError`
  distinguishes "load failed" from "genuinely zero"; hero renders an honest error state instead.
- **30s poll fetches the entire lifetime payload.** `ActiveSessionContext.tsx:25` polls
  `getMyStats` every 30s solely to find one active session; the handler returns **all** sessions
  ever (no `Take()`), and the DTO field named `RecentSessions` is actually the complete history —
  a misleading name that Home's week-P&L derivation silently depends on.

### Navigation / IA
- **Track hub ignores its `segment` param after first mount** (`TrackScreen.tsx:50`). Tab screens
  stay mounted, so Home's "Full stats" / "See all" land on whichever segment was last open. Class:
  any always-mounted tab screen honouring route params needs a param-sync effect.

### Retention honesty (the class this project keeps re-shipping)
- **Streak/freeze maintenance runs only at cold start** (`StudyContext.tsx:87`). Mobile apps live
  suspended for days; a user returning after two days sees a stale "alive" streak, never gets the
  auto-freeze their token entitles them to, and the reminder scheduler reads the stale value.
- **`streak_risk` reminder repeats nightly forever.** `reminders.ts:80` — no `fireAtMs`, so it
  schedules `{hour: 20, repeats: true}`; eligibility is only re-evaluated on app foreground. A user
  who studies Monday and never reopens gets "your streak is at risk" **every night forever**, false
  from ~day 2. This directly violates the pillar's own standing rule that no reminder may make an
  untrue claim, and unbounded nagging drives permission revocation.
  **✅ RESOLVED PR #76** (merged 2026-08-05): converted to a one-shot `fireAtMs` for today only
  (mirrors `game_day`'s pattern), skipped once today's fire hour has passed.

### Privacy
- **Opt-out-period events leak on re-opt-in after restart.** `analytics.ts:144` — the buffer keeps
  accumulating while opted out; if the app *started* opted-out and the user later opts back in, the
  fresh client's drain loop captures up to 200 events generated while sharing was explicitly OFF.
  The same-session path is correct; only the cold-start path leaks. Exactly the untested corner.

### Latent landmines behind dark flags (fix before the flag flips, not after)
- **Cloud Sync restore is invisible to the UI and gets clobbered** by the next mutation
  (`cloudSyncService.ts:144` bypasses `LocalGamesContext`); the **Auto-sync toggle is wired to
  nothing** — a false promise the day `cloud_sync` goes live.
- **Lesson lock is enforced only at the link source** (`LessonReaderScreen.tsx:45`) while all 28
  modules' full text ships in the bundle. Latent today (no route reaches a locked id), live the
  moment any new entry point forgets the source-side check.

### Product-credibility
- **Every non-Israeli user is locked to ₪ ILS.** `features.ts:46` — `currencyPrefs` is OFF in prod,
  so the finished picker, Intl formatting for 6 currencies and locale detection are all dead code
  in production. For a money tracker on a global store, this is a first-session credibility hit.
- **Reminder prefs toggles show ON when nothing can fire** (permission denied, or on web where every
  reminders call is a no-op). CLAUDE.md claims this screen drives "honest toast copy"; the screen
  contains no toast at all — a documented guarantee that is untrue exactly where it matters.

### Marketing — an honesty pin that inverted
- **The landing site denies the live iOS app.** `apps/landing/lib/stores.ts:2` — badges render
  disabled "Coming soon", `HERO.storeNote` says "Mobile apps coming soon", **and
  `__tests__/honesty.test.ts` asserts the badges carry NO href** — so the pin that once prevented
  over-claiming now *enforces under-claiming* and structurally blocks linking the live listing.
  The landing is the single indexable search entry point, so a searcher cannot reach the iOS app
  from it at all.

  ⚠️ The audit agent proposed a specific App Store ID for the fix. **Do not take that on trust** —
  the real listing URL must be confirmed by the owner before it ships.
  **✅ RESOLVED PR #77** (merged 2026-08-05): owner supplied and verified the real URL
  (`https://apps.apple.com/app/t-poker-poker-trainer/id6781109023`, used exactly as given, not
  agent-proposed); `StoreBadge.href` is now optional and present only for a store where the app
  has genuinely shipped — App Store links out for real, Google Play stays disabled (no listing).

## Deferred findings — recorded for the security/privacy pass, deliberately NOT fixed in the deletion slice

These surfaced while fixing the account-deletion defect (PR #74). Owner decision 2026-08-03: record,
don't fix in that slice.

### Erasure is inverted — the PII-free rows are deleted, the PII-bearing ones survive
`DeleteAccountCommandHandler` removes Settlements, which store only GUIDs and never a name. The
departing user's **display name survives in plaintext** in surfaces the handler never touches:
`ActivityLog.ActorName` and its interpolated `Description`, `HandRecord.WinnerName`, and other
users' `Notification` bodies (e.g. `MarkSettlementPaidCommandHandler` writes
`"{payerName} marked a settlement of … as paid."` into the counterparty's inbox). `ActivityLog`'s
actor column is an unmapped plain `Guid`, so nothing cascades. Given the Danger Zone copy promises
"permanently delete your account and all associated data" and iOS is live under 5.1.1(v), this is a
compliance-adjacent gap, not only a tidiness one. Either scrub those strings on deletion or stop
implying they are covered.

### A refusal that names an action the API does not expose
Group owners still cannot delete their account. The refusal reads "Transfer ownership or delete the
groups before deleting your account" — but **no transfer endpoint exists**;
`Group.TransferOwnership` is called from exactly one place, `LeaveGroupCommandHandler`, as a side
effect of leaving. On a path Apple requires to be completable in-app, the instruction points at a
control the product does not have. That is its own honesty defect (a promise of a capability that
does not ship), separate from the compliance question of whether owners should be able to delete
at all.

### RemovePlayer/AddBuyIn race mints orphaned money rows (pre-existing, live today)
Found 2026-08-04 by the PR #74 disposition fleet, demonstrated end-to-end with the real handlers:
`BuyIn/CashOut.SessionPlayerId` is **ON DELETE SET NULL**, and `RemovePlayerCommandHandler`'s
Active branch deletes a seat's money rows from lists read before its transaction — a buy-in
committed concurrently by another group member (two devices at one table) survives the
`RemoveRange` and is SET-NULL'd by the seat delete, yielding a `(SessionPlayerId=null,
UserId=null)` row with **no account deletion involved**. A same-class variant exists on the
Draft branch (concurrent `AddBuyIn` auto-starts the session; that branch deletes the seat
without touching money rows — hits registered players too). On the live build the orphaned
amount is **silently dropped** from every calculation; after PR #74 the session is loudly
refused instead (the refusal message was reworded during disposition so it does not claim a
deletion it cannot prove). Fix belongs in `RemovePlayerCommandHandler` (transactional removal +
deleting the SET-NULL'd rows before commit, both branches) — **its own slice**, not part of the
deletion PR.
**✅ RESOLVED PR #78** (merged 2026-08-05): the Active branch's buy-in/cash-out cleanup (unchanged
`ToListAsync`+`RemoveRange`) is unified into one block that runs for BOTH branches, positioned
after both guard clauses instead of nested inside either — the Draft branch previously had none
at all. Honest limit stated in the handler: this does not add locking, so the pre-existing
narrow read-then-remove window on the Active branch is unchanged; closing that fully needs
serializable isolation or locking coordinated with `AddBuyIn`, out of scope for that fix.

### Deferred alternative to the settlement guard
The chosen fix (PR #74) refuses to recalculate a session containing a deleted player, which
prevents the data loss without touching the schema. The richer option — making
`Settlement.PayerUserId`/`ReceiverUserId` nullable so the departed party is anonymised rather than
removed, preserving the debt and its paid status — needs a migration plus a DTO change reaching the
mobile client. Deferred by owner decision 2026-08-03; revisit if the richer behaviour is ever
needed.

## Wave 1 findings (2026-08-05) — auth/authz+IDOR, API/backend, live-money, bankroll

Severity scale for this security+audit pass (distinct from the critical/major/minor/nit scale
used in the ORIGINAL 4 sections above): **critical** = exploitable now, live-money or full-account
compromise · **high** = real risk, needs a specific precondition · **medium** = defense-in-depth
gap · **low** = hardening opportunity · **informational** = worth knowing, not urgent. Roughly:
critical≈critical, high≈major, medium/low≈minor, informational≈nit.

### HIGH

**Any authenticated user can attach ANY other registered user to a session's ledger without
consent, then generate real settlement debts against them, with no recourse to leave**
`src/PokerApp.Application/Features/Sessions/Commands/AddPlayer/AddPlayerCommandHandler.cs:54-71`,
enabled by the unscoped `SearchUsersQueryHandler` (`src/PokerApp.Application/Features/Users/Queries/SearchUsers/SearchUsersQueryHandler.cs:10-19`)
and raw client-controlled `UserId` in `SessionsController.cs:311`.
Any user can create a standalone session (no group required), search for ANY registered user by
username substring (zero group-membership scoping), add them by Guid to the session's ledger with
only an "already added" check, record buy-ins/cash-outs against them, and `CalculateSettlements`
persists a real `Settlement` row naming the victim — which the victim then sees in their own
pending-settlements list and gets notified about when "paid". `RemovePlayerCommandHandler`
requires the CALLER to be the session creator or a group admin — the **victim has no path to
remove their own forced seat**, and once the session is Active, registered-player removal is
blocked entirely until Finished. This bypasses the consensual `SessionInviteToken` system
(single-use, 24h) that exists for exactly this purpose. **Fix:** route registered-user additions
through the invite-token flow only (or a Pending/Invited SessionPlayer state requiring accept),
and let the target remove their own seat regardless of session status. Scope `SearchUsersQuery`
to shared-group members.

**`RedeemTopUp` grants paid AI credits with no purchase-receipt verification — a dormant
credit-forgery bug behind a config flag, not a code guard**
`src/PokerApp.Application/Features/Billing/Commands/RedeemTopUp/RedeemTopUpCommand.cs:36-52`;
`TopUpCatalog.cs:14-20`; `TopUpSettings.cs:16`.
Unlike `ValidatePurchaseCommandHandler` (which calls `IBillingVerifier.VerifyAsync` — real Apple
JWS / Google OIDC / Stripe HMAC verification), `RedeemTopUpCommandHandler` only does a config
lookup on the client-supplied `ProductId` and grants credits unconditionally, keyed by an
idempotency string built from the client-supplied `PurchaseToken` — nothing ties that token to a
real purchase. Inert TODAY only because `TopUpSettings.Enabled` defaults `false` with an empty
bundle list in every appsettings file; the moment top-ups are enabled for app-store billing
launch, any authenticated user can mint free AI credits repeatably (any new token string is a new
idempotency key). **Fix:** call `IBillingVerifier.VerifyAsync` before granting, same as
`ValidatePurchase`, using the store-confirmed transaction id as the idempotency key — before
`TopUpSettings.Enabled` is ever flipped true anywhere. Consider a startup fail-loud check
(mirroring the existing prod billing/CORS `LogCritical` pattern) refusing to boot with
`Enabled=true` while no verifier call exists in the redeem path.

**`EndSession` has no concurrency guard — concurrent end-game submits duplicate `CashOut` rows and
corrupt settlement totals**
`src/PokerApp.Application/Features/Sessions/Commands/EndSession/EndSessionCommandHandler.cs:38-59`.
`Session` carries no concurrency token anywhere (repo-wide grep of Configurations for
`IsConcurrencyToken`/`IsRowVersion`: zero hits), so the read-check-then-mutate pattern against
`session.Status` is a real TOCTOU window — two concurrent "End Game & Settle" submits (two admins,
or a client retry after a timeout while the original request is still in flight) can both pass
the `Status == Active` guard and each insert a full set of `CashOut` rows from `FinalStacks`.
`CalculateSettlements`/`GetSessionBalances` sum ALL `CashOut` rows per seat with no dedupe, so the
duplicate directly doubles a player's counted cash-out. The same TOCTOU class PR #78 fixed for
`RemovePlayer`, a different instance, not yet hit. **Fix:** add a concurrency/version column to
`Session` (EF `[Timestamp]`/rowversion) so the losing writer gets a `DbUpdateConcurrencyException`
→ 409; or make `FinalStacks` idempotent per session (reject if any `CashOut` already exists when
`FinalStacks` is non-empty).

### MEDIUM

- **Webhook endpoints unauthenticated with no rate limiting, unbounded raw-body reads before
  signature check.** `WebhooksController.cs:20-79` — Stripe/Paddle/RevenueCat read the full body
  into a string before any HMAC/JWS check; no `[EnableRateLimiting]`, no `[RequestSizeLimit]`
  (Kestrel's ~28.6MB default applies). Add a per-IP rate limit + explicit request-size cap.
- **`AddBuyIn` auto-starts a Draft session for any group member, bypassing the admin/owner-only
  Start rule.** `AddBuyInCommandHandler.cs:22-39` vs `StartSessionCommandHandler.cs:22-34` — the
  latter enforces `GroupRole.Member` cannot start a session; the former performs the identical
  `Draft → Active` transition via `session.Start()` with no role check at all. Extract the role
  check into one shared enforcement point.
- **Buy-in/cash-out/hand-record authorization is scoped to the whole group, not session
  participants or a host role.** `AddBuyInCommandHandler.cs`/`AddCashOutCommandHandler.cs`/
  `AddHandRecordCommandHandler.cs:22-29` — any group member (any role) can record money against
  ANY player in that group's session, including players they're not seated with. May be
  deliberate ("any member can scorekeep") but should be a documented decision, not an emergent
  property of a read-screen `hasAccess` helper reused for money writes.
- **Session invite-token redemption is not atomic — two concurrent joins can both consume a
  "single-use" token.** `JoinSessionByTokenCommandHandler.cs:21-49` — no concurrency token, only
  a unique index on the token string itself. Same TOCTOU class as `EndSession` above; fix as a
  conditional `UPDATE ... WHERE UsedAt IS NULL` checking rows-affected.
- **Bankroll `AsyncStorage` is unscoped by user — session data crosses login boundaries on shared
  devices.** `bankrollStore.ts:20` — single hardcoded key `tpoker.bankroll.v1`, never cleared or
  namespaced on logout (`AuthContext.clearSession()` doesn't touch it). User A's venue names/
  notes/P&L are visible to User B on the same device after a account switch. Broader exposure
  than the equivalent, documented-as-ephemeral local-games gap, since Bankroll is positioned as
  personal financial tracking and reachable from the signed-in tab bar.

### LOW

- **Authenticated billing endpoints and `ChangePassword` have no rate limiting.**
  `BillingController.cs:26-58`, `AuthController.cs:150-161` — only login/register/refresh/
  coach-analyze have `[EnableRateLimiting]`. A stolen-but-valid access token allows unlimited
  `CurrentPassword` brute-force attempts.
- **`LogoutCommandHandler` revokes whatever refresh token is supplied without checking it belongs
  to the caller.** `LogoutCommandHandler.cs:11-27` — not independently exploitable (possessing
  another user's plaintext refresh token is already full compromise) but inconsistent with every
  other handler's ownership-check pattern; tighten as defense-in-depth.
- **Settlement tie-break ordering differs between the TS local engine and the C# server engine.**
  `local/settlements.ts:51-54` sorts ties by `playerId.localeCompare`; `SettlementCalculatorService.cs:9-19`
  has no secondary sort key. Totals always match; the *specific* pairing for tied balances can
  legally differ between a synced local game and the server calculation. Add the same secondary
  key server-side + a tied-balance fixture to the shared pinned test set.
- **`AddPlayer`'s duplicate-guest-name check has the same read-then-insert race as the findings
  above.** `AddPlayerCommandHandler.cs:36-52` — two concurrent "Add Guest" taps with the same name
  can both pass the pre-check and both insert. Add a unique index on `(SessionId, GuestName)`.
- **Advanced bankroll analytics ships fully built and free while `premium/config.ts` still calls
  it unbuilt, with no entitlement gate to retrofit.** `premium/config.ts:74-91` marks
  `advanced_bankroll` `comingSoon: true`; `BankrollScreen.tsx:181-208` already renders the exact
  feature (variance/drawdown/histogram), free, with zero `useEntitlements`/`LockNudge` call
  anywhere in the bankroll tree. No live harm today (flag off in prod, nothing chargeable) but the
  comment is already false and there's no gate to flip on before Bankroll goes live in prod.

### INFORMATIONAL

- CSP is `Content-Security-Policy-Report-Only`, not enforced (`SecurityHeaderPolicy.cs:18`) —
  flagged in its own doc comment as intentional pending tuning; confirm there's a follow-up.
- `JwtService.GenerateAccessToken` re-derives the signing key directly from `settings.SecretKey`
  instead of routing through `JwtKey.ResolveSigningKey` (used only on the validation side) — not
  currently exploitable (Program.cs's fail-closed check runs before any token is ever signed) but
  a future refactor could let signing and validation silently diverge.
- Apple Sign-In skips nonce replay-protection entirely when the client omits the nonce field
  (`AppleAuthService.cs:54-58`) — not independently exploitable (Apple's identity token can't be
  forged) but nonce isn't enforced as required on `AppleLoginCommand`; make it `NotEmpty()`.
- `GroupRole.Owner` vs `Groups.OwnerId` divergence (an open question from the original audit,
  line 38-40 above) — **verified NOT reachable**: exactly two call sites ever write either value,
  both mutate both columns together in the same handler before one `SaveChangesAsync`. Consider a
  structural pin (SaveChanges interceptor or DB check) so this stays true as the codebase grows.
- Tournament `rebuyCount`/`addOnCount` are hardcoded to 0-or-1 regardless of actual count entered
  (`LogSessionScreen.tsx:122-123`) — write-only today (no read site found), but any future feature
  reading these fields will silently get wrong data for every historical row logged so far.
