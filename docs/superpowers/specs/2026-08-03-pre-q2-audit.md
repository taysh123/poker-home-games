## CRITICAL — ships today, App Store compliance risk

### Account deletion 500s for any user with settlement history
`src/PokerApp.Application/Features/Auth/Commands/DeleteAccount/DeleteAccountCommandHandler.cs:47`

The handler removes memberships, received invitations and refresh tokens, and anonymises
`SessionPlayer.UserId` — but never touches **Settlements** (`PayerUserId`/`ReceiverUserId`, required
FKs with `DeleteBehavior.Restrict`), **`SessionPlayer.LinkedUserId`** (Restrict), or **group
invitations the user SENT** (`InvitedByUserId`, Restrict). `context.Users.Remove(user)` then throws
`DbUpdateException` at `SaveChangesAsync`, which `ExceptionHandlingMiddleware` does not map — so the
live app returns a generic 500 and the user sees "Failed to delete account."

Any user whose finished session ever had settlements calculated — **exactly the engaged users** —
cannot delete their account. iOS 1.1.1 is live; **App Store Guideline 5.1.1(v) requires working
in-app account deletion**, and the Danger Zone copy promises "permanently delete your account and
all your data." There is no backend test for `DeleteAccount`.

This is a CLASS: no handler that deletes a user-owned aggregate has an integration test proving the
delete actually succeeds against the real FK graph. The guard is an integration test per
delete-path, seeded with the FK shapes that exist in production.

**Disposition: its own slice, before any Q2 pillar work.** It is a live-compliance defect on a
shipped app; Q2 is polish by comparison.

## MAJOR — grouped by theme

### Money/data correctness on the front door
- **Home has no error state.** `HomeScreen.tsx:160` — three of the seven load calls have no
  `.catch`; any failure rejects the batch into a silent `catch {}`, and the hero then renders
  `stats?.totalProfitLoss ?? 0` as an animated **₪0 "Break even"** with "0 sessions". A network
  blip shows a returning user confidently wrong money. *Never `?? 0` for money* is the class rule.
- **30s poll fetches the entire lifetime payload.** `ActiveSessionContext.tsx:25` polls
  `getMyStats` every 30s solely to find one active session; the handler returns **all** sessions
  ever (no `Take()`), and the DTO field named `RecentSessions` is actually the complete history —
  a misleading name that Home's week-P&L derivation silently depends on.

### Navigation / IA
- **Track hub ignores its `segment` param after first mount** (`TrackScreen.tsx:50`). Tab screens
  stay mounted, so Home's "Full stats" / "See all" land on whichever segment was last open. Class:
  any always-mounted tab screen honouring route params needs a param-sync effect.

### Retention honesty (the class this project keeps re-shipping)
- **Streak/freeze maintenance runs only at cold start** (`StudyContext.tsx:87`). Mobile apps live
  suspended for days; a user returning after two days sees a stale "alive" streak, never gets the
  auto-freeze their token entitles them to, and the reminder scheduler reads the stale value.
- **`streak_risk` reminder repeats nightly forever.** `reminders.ts:80` — no `fireAtMs`, so it
  schedules `{hour: 20, repeats: true}`; eligibility is only re-evaluated on app foreground. A user
  who studies Monday and never reopens gets "your streak is at risk" **every night forever**, false
  from ~day 2. This directly violates the pillar's own standing rule that no reminder may make an
  untrue claim, and unbounded nagging drives permission revocation.

### Privacy
- **Opt-out-period events leak on re-opt-in after restart.** `analytics.ts:144` — the buffer keeps
  accumulating while opted out; if the app *started* opted-out and the user later opts back in, the
  fresh client's drain loop captures up to 200 events generated while sharing was explicitly OFF.
  The same-session path is correct; only the cold-start path leaks. Exactly the untested corner.

### Latent landmines behind dark flags (fix before the flag flips, not after)
- **Cloud Sync restore is invisible to the UI and gets clobbered** by the next mutation
  (`cloudSyncService.ts:144` bypasses `LocalGamesContext`); the **Auto-sync toggle is wired to
  nothing** — a false promise the day `cloud_sync` goes live.
- **Lesson lock is enforced only at the link source** (`LessonReaderScreen.tsx:45`) while all 28
  modules' full text ships in the bundle. Latent today (no route reaches a locked id), live the
  moment any new entry point forgets the source-side check.

### Product-credibility
- **Every non-Israeli user is locked to ₪ ILS.** `features.ts:46` — `currencyPrefs` is OFF in prod,
  so the finished picker, Intl formatting for 6 currencies and locale detection are all dead code
  in production. For a money tracker on a global store, this is a first-session credibility hit.
- **Reminder prefs toggles show ON when nothing can fire** (permission denied, or on web where every
  reminders call is a no-op). CLAUDE.md claims this screen drives "honest toast copy"; the screen
  contains no toast at all — a documented guarantee that is untrue exactly where it matters.

### Marketing — an honesty pin that inverted
- **The landing site denies the live iOS app.** `apps/landing/lib/stores.ts:2` — badges render
  disabled "Coming soon", `HERO.storeNote` says "Mobile apps coming soon", **and
  `__tests__/honesty.test.ts` asserts the badges carry NO href** — so the pin that once prevented
  over-claiming now *enforces under-claiming* and structurally blocks linking the live listing.
  The landing is the single indexable search entry point, so a searcher cannot reach the iOS app
  from it at all.

  ⚠️ The audit agent proposed a specific App Store ID for the fix. **Do not take that on trust** —
  the real listing URL must be confirmed by the owner before it ships.
